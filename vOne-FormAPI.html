vOne-FormAPI

Records the mapping between a website / product form submission and the support tickets raised for it in vOne and VKS. ASP.NET Core on AWS Lambda, persisting to PostgreSQL. One developer-facing route: POST /ticket. The service emits no queue / topic / event messages — it only writes to its database.

01 Overview

vOne-FormAPI is a small write-only microservice in the VIDYAOne SaaS platform.

  • POST /ticket — create or update ("upsert") the row in public.tbl_form_ticket that links one form submission (requestId) to its vOne ticket and its VKS ticket. No application-layer authentication (see §03).
There is also a bare GET {base} route that returns a one-line text/plain "application / environment" string. Unlike /ticket it is behind the vAccount SaaS cookie, and is only useful as a reachability check — it is not part of the API contract.

03 Authentication

POST /ticket has no application-layer authentication. Its path is on the SaaS-cookie middleware's skip list, and the controller carries no auth filter — the request reaches the handler with no identity check. There is no API key, bearer token, cookie or query-string auth on this route.

Access must be restricted upstream. Because the app performs no auth on /ticket, only AWS API Gateway / network controls stand between a caller and a write to tbl_form_ticket. Confirm the gateway restricts this route before relying on it.
  • Callers: send the JSON body with Content-Type: application/json. No Cookie or Authorization header is required or inspected.
  • GET {base} (reachability check only) is the one route still behind the vAccount SaaS common-auth cookie (vacc-common-auth, an HttpOnly signed session cookie; signing key from DynamoDb:CookieConfigKey). Missing / expired / invalid → 401. In Development the middleware substitutes a fixed dev identity.
  • CORS / preflight: OPTIONS is answered with 200 before anything else; the actual Access-Control-Allow-* headers are emitted by AWS API Gateway, not by application code. Confirm the allowed-origin list with the platform team.

05 POST /ticket

Upsert the link between a form submission and its downstream tickets. Call this once the vOne and VKS tickets for a submitted form have been created, to persist which ticket IDs / numbers belong to that requestId. Keyed on requestId — calling it again for the same requestId overwrites the four ticket fields in place. Safe to retry.

Response

200 OK

Returned whether the row was inserted or updated — the response does not distinguish the two.

{
  "success": true,
  "message": "Success.",
  "data": null,
  "errors": null
}

Behaviour — upsert & revive (worked example)

  • First call for requestId = R → a new tbl_form_ticket row is inserted (is_active = true, is_deleted = false).
  • Second call for the same R with different ticket numbers → the existing row's v_one_ticket_id/number, vks_ticket_id/number and updated_at are overwritten. request_id and created_at are untouched.
  • If that row had been soft-deleted (is_deleted = true), the same update also revives it: is_active = true, is_deleted = false, inactive_at = null, deleted_at = null.
  • Idempotent: sending the same body twice leaves exactly one row in the same final state. There is no create-vs-update signal in the response and none is needed.

Error responses

400 · VALIDATION_FAILED

Any required field missing, empty, or over its length limit; or an empty / unparseable JSON body.

{
  "success": false,
  "message": "Validation failed.",
  "errors": [
    { "code": "VALIDATION_FAILED", "message": "RequestId is required.", "field": "PostDTO.RequestId" },
    { "code": "VALIDATION_FAILED", "message": "VksTicketNumber must not exceed 50 characters.", "field": "PostDTO.VksTicketNumber" }
  ]
}

Do not retry without correcting the body.

409 · CONCURRENCY_CONFLICT

Rare. A concurrent request inserted and then deleted the same requestId row in the small window between this request's update-probe and its insert-retry. 

{
  "success": false,
  "message": "Tbl_Form_Ticket was modified by another process. Key=798930e2-58de-4ab4-8aa3-906e76faaa1d. Please reload and retry."
}

Retry after a short backoff — it is transient.

415 · INVALID_INPUT

Content-Type is not application/json.

{
  "success": false,
  "message": "Unsupported media type.",
  "errors": [ { "code": "INVALID_INPUT", "message": "Unsupported media type." } ]
}
500 · INTERNAL_ERROR

Unexpected database / server error (connectivity, an unforeseen constraint violation, …). Detail is hidden outside Development.

{
  "success": false,
  "message": "An unexpected error occurred."
}

Retry with exponential backoff; escalate if it persists.

General limits

  • Rate limits: none in application code. Any throttling is at API Gateway — check with the platform team.
  • Request body size: bounded by the API Gateway payload limit (~10 MB for HTTP APIs); an unreadable / oversized body returns 400 "Malformed or unreadable request."
  • Timestamps: stored as timestamptz, always UTC.
  • No pagination / async / events: the route is a synchronous single write; nothing is queued and no message is published downstream.
