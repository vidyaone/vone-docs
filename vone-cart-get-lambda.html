vone-cart-get-lambda

API reference for the cart read endpoint — query parameter, response shape, and field reference.

GET only (+ OPTIONS preflight) ap-south-1 CORS: *.vidyaone.com (https only) Max items: 1000 per guest_id
Request Query parameter Response item fields Validation & rejection Example requests Responses Request flow

01 Request

A plain GET request — no body. The guest's identifier is passed as a single query string parameter. 

GET /cart?guest_id=guest_a1b2c3d4 HTTP/1.1
Host: api.vidyaone.com

02 Query parameter

ParameterTypeRequirementRule
guest_idstringrequiredNon-blank after trim, 1–100 chars, ^[A-Za-z0-9_-]+$ only.

Read from queryStringParameters.guest_id only — there is no path-parameter or body fallback. The value is not treated as a secret credential by this Lambda; it is only sanitized/length-capped before being used to build the DynamoDB partition key (GUEST#<guest_id>).

03 Response item fields

Each object in data mirrors the original client-submitted payload shape from vone-cart-post-lambda — no internal keys (pk/sk), no server-generated bookkeeping (requestId, submittedAt, status), and no enrichment data (device, location, botDetection) are ever returned. Fields are fetched via a DynamoDB ProjectionExpression, so nothing else is even read off the table.

04 Validation & rejection

  • guest_id missing from the query string entirely → 400.
  • guest_id present but blank/whitespace-only → 400.
  • guest_id containing anything outside [A-Za-z0-9_-], or longer than 100 characters → 400.

Common rejection messages

  • Missing required query parameter 'guest_id'
  • Query parameter 'guest_id' must not be blank
  • Query parameter 'guest_id' contains invalid characters

A guest_id that passes validation but has never been used (or whose cart is empty) is not an error — it returns 200 with "data": []. There is no way (and no need) to distinguish "never used" from "emptied cart".

05 Example requests

✅ Valid — cart with items

GET /cart?guest_id=guest_a1b2c3d4

✅ Valid — empty cart

GET /cart?guest_id=guest_never_used

❌ Rejected — missing guest_id

GET /cart
// 400 — "Missing required query parameter 'guest_id'"

❌ Rejected — blank guest_id

GET /cart?guest_id=
// 400 — "Query parameter 'guest_id' must not be blank"

❌ Rejected — disallowed characters

GET /cart?guest_id=<script>
// 400 — "Query parameter 'guest_id' contains invalid characters"

Returned for any guest_id validation failure (see §04).

500 Internal Server Error
{
  "success": false,
  "message": "Internal server error",
  "errors":  null,
  "data":    []
}

Returned only for an unexpected exception (DynamoDB outage, missing IAM permission, bad table config, etc.). The specific cause is logged in CloudWatch with an actionable hint — never leaked to the caller.

CORS headers

Applied to every response (200/400/500/204) when the request's Origin header is https://vidyaone.com or any https://*.vidyaone.com subdomain — http and unrecognized origins get no CORS headers at all, so a browser blocks the page from reading the response. Non-browser callers (no Origin header) are unaffected — the response body is still returned normally.

  • Access-Control-Allow-Origin — reflected request origin (only if allowed)
  • Access-Control-Allow-Methods: GET,OPTIONS
  • Access-Control-Allow-Headers: Content-Type
  • X-Content-Type-Options: nosniff, X-Frame-Options: DENY, Strict-Transport-Security, Cache-Control: no-store, no-cache, must-revalidate — always present, regardless of origin

07 Request flow

Request → lambda_handler │ ├─ method == OPTIONS? → 204, no processing │ └─ GET → EventParser.parse(event) │ ├─ guest_id present in queryStringParameters, else 400 ├─ non-blank after strip, else 400 ├─ charset/length ^[A-Za-z0-9_-]{1,100}$, else 400 │ └─ DbHelper.get_items_by_guest_id(guest_id) │ ├─ Query DynamoDB pk = GUEST#<guest_id> ├─ ProjectionExpression original-payload fields only (no pk/sk/device/location/botDetection) ├─ paginate via LastEvaluatedKey, capped at MAX_ITEMS_PER_GUEST (1000) ├─ Decimal → float/int price/discount/total always float ├─ merge item defaults for any attribute missing on a legacy record │ └─ 200 { success: true, message: "", errors: null, data: [...items] }

Any exception raised while building the DB client or running the query — not just the query itself — is caught by the same handler and mapped to a 500, so an infrastructure failure never produces an unhandled/malformed response.
