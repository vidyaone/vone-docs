vone-cart-get-lambda

API reference for the cart read endpoint — query parameters, response shape, and field reference.

GET only (+ OPTIONS preflight) ap-south-1 CORS: *.vidyaone.com (https only) Lookup: guest_id and/or user_id Max items: 1000 per response
Request Query parameters Lookup behaviour Response item fields Validation & rejection Example requests Responses Request flow

01 Request

A plain GET request — no body. The cart is looked up by guest_id, user_id, or both, passed as query string parameters. At least one of the two must be present. 

GET /cart?guest_id=guest_a1b2c3d4 HTTP/1.1
Host: api.vidyaone.com

02 Query parameters

ParameterTypeRequirementRule
guest_idstringconditionalNon-blank after trim, 1–100 chars, ^[A-Za-z0-9_-]+$ only. Required unless user_id is supplied.
user_idinteger (as string)conditionalDigits only, ^[0-9]{1,20}$, value > 0. Required unless guest_id is supplied.

Read from queryStringParameters only — there is no path-parameter or body fallback. At least one of guest_id / user_id must be present; supplying neither is a 400. Supplying both is allowed and triggers a merged lookup (see §03). Neither value is treated as a secret credential — each is only sanitized/bounded before use: guest_id builds the DynamoDB partition key (GUEST#<guest_id>); user_id is coerced to an integer and matched against the userId item attribute.

03 Lookup behaviour

The two parameters resolve items by different mechanisms, then results are combined.

ParameterMechanismCost
guest_idDynamoDB Query on pk = GUEST#<guest_id>Key lookup — fast, single partition.
user_idDynamoDB Scan with FilterExpression userId = <n>expensive The table has no GSI on userId, so every partition is scanned and filtered. Read-capacity cost and latency grow with table size. Logged with [WARN] on every call.

Merge & de-duplication (both parameters supplied)

guest_id is read first, then user_id. The two result sets are concatenated and de-duplicated on the item's internal sort key (sk = REQUEST#<request_id>); on a collision the guest_id copy is kept. The internal key is stripped before the response is returned. The combined result is still capped at 1000 items.

Worked example. A logged-in shopper (userId = 7) has cart items saved under session guest_g1; the same account also has one older item from session guest_g2. 

GET /cart?guest_id=guest_g1&user_id=7

// Query  pk = GUEST#guest_g1        -> REQUEST#r1 (userId 7), REQUEST#r2 (userId 0)
// Scan   userId = 7                 -> REQUEST#r1 (guest_g1), REQUEST#r3 (guest_g2)
// Merge + dedupe on sk              -> r1 (guest copy kept), r2, r3
// data: 3 items

04 Response item fields

Each object in data mirrors the original client-submitted payload shape from vone-cart-post-lambda — no internal keys (pk/sk), no server-generated bookkeeping (requestId, submittedAt, status), and no enrichment data (device, location, botDetection) are ever returned. Fields are fetched via a DynamoDB ProjectionExpression, so nothing else is even read off the table.

"Default if missing" only applies to legacy/edge-case records that lack an attribute — every item in data always has the full 15-field shape, merged in by the Lambda, so client-side code never has to guard against a missing key.

05 Validation & rejection

  • Neither guest_id nor user_id present in the query string → 400.
  • guest_id present but blank/whitespace-only → 400.
  • guest_id containing anything outside [A-Za-z0-9_-], or longer than 100 characters → 400.
  • user_id present but blank/whitespace-only → 400.
  • user_id non-numeric, more than 20 digits, or not > 0 (e.g. 0, -3, 12x) → 400.

Each parameter is validated independently: a present-but-malformed value is a 400 even if the other parameter is valid.

Common rejection messages

  • Provide at least one of query parameters 'guest_id' or 'user_id'
  • Query parameter 'guest_id' must not be blank
  • Query parameter 'guest_id' contains invalid characters
  • Query parameter 'user_id' must not be blank
  • Query parameter 'user_id' must be a positive integer

A guest_id/user_id that passes validation but has never been used (or whose cart is empty) is not an error — it returns 200 with "data": []. There is no way (and no need) to distinguish "never used" from "emptied cart".

500 Internal Server Error
{
  "success": false,
  "message": "Internal server error",
  "errors":  null,
  "data":    []
}

Returned only for an unexpected exception (DynamoDB outage, missing IAM permission — the role needs both dynamodb:Query and dynamodb:Scan — bad table config, etc.). The specific cause is logged in CloudWatch with an actionable hint — never leaked to the caller.

CORS headers

Applied to every response (200/400/500/204) when the request's Origin header is https://vidyaone.com or any https://*.vidyaone.com subdomain — http and unrecognized origins get no CORS headers at all, so a browser blocks the page from reading the response. Non-browser callers (no Origin header) are unaffected — the response body is still returned normally.

  • Access-Control-Allow-Origin — reflected request origin (only if allowed)
  • Access-Control-Allow-Methods: GET,OPTIONS
  • Access-Control-Allow-Headers: Content-Type
  • X-Content-Type-Options: nosniff, X-Frame-Options: DENY, Strict-Transport-Security, Cache-Control: no-store, no-cache, must-revalidate — always present, regardless of origin

08 Request flow

Request → lambda_handler │ ├─ method == OPTIONS? → 204, no processing │ └─ GET → EventParser.parse(event) │ ├─ guest_id if present: non-blank + ^[A-Za-z0-9_-]{1,100}$, else 400 ├─ user_id if present: non-blank + ^[0-9]{1,20}$ + > 0, else 400 ├─ at least one of guest_id / user_id present, else 400 │ └─ DbHelper.get_items(guest_id, user_id) │ ├─ guest_id → Query pk = GUEST#<guest_id> ├─ user_id → Scan FilterExpression userId = <n> (no GSI — full-table scan, logged [WARN]) ├─ ProjectionExpression original-payload fields + sk (sk used only for de-dup) ├─ paginate each read via LastEvaluatedKey, each capped at MAX_ITEMS_PER_GUEST (1000) ├─ merge both result sets, de-dupe on sk (guest_id copy wins), re-cap at 1000 ├─ strip sk; Decimal → float/int (price/discount/total always float) ├─ merge item defaults for any attribute missing on a legacy record │ └─ 200 { success: true, message: "", errors: null, data: [...items] }

Any exception raised while building the DB client or running the query — not just the query itself — is caught by the same handler and mapped to a 500, so an infrastructure failure never produces an unhandled/malformed response.
