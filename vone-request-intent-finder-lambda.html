vone-request-intent-finder-lambda

Developer reference for the intent-classification API (region: ap-south-1). Takes a raw inbound request from a VIDYAOne intake channel, asks Claude (via Amazon Bedrock) to work out the requester's intent, and returns a normalized form payload.

Authentication & CORS

No application-level authentication. lambda_function.lambda_handler does not check an API key, bearer token, or session cookie on any request — every well-formed {"channel": ..., "data": {...}} body is processed regardless of caller identity. If API Gateway enforces an API key, usage plan, or IAM auth in front of this Lambda, that's configured outside this repository — consult the API Gateway console for the current state.

CORS is handled entirely at API Gateway — this Lambda's code never sets any Access-Control-* header itself.

Endpoint: Find Intent

Summary

Call this when a raw submission arrives on one of VIDYAOne's intake channels — a call transcript, an inbound email, a WhatsApp message, a website form submit, or an AI-chat transcript — and you need it classified into a VIDYAOne form category with structured fields extracted (name, contact details, institution, etc.) before routing it onward. One call classifies one submission; there is no batch mode.

Error & degraded responses

Every one of these keeps the exact same five-key body shape — only ai_result.ok/errors, the HTTP status, and (usually) form_type falling back to "other" change.

StatusWhen it firesRetry?
400 Bad envelope — missing channel/data, unknown channel, a missing required field for that channel, or a malformed JSON body. No — fix the request. ai_result.errors names exactly what's wrong.
200 Degraded — request was valid but the model never ran: too little Lambda time budget remaining, the model refused, returned unparseable output, or didn't call the required tool. form_type is "other"; subject/message are still the real values from your request, so it's still routable by a human. Optional — the response is still usable as-is; retry only if you want an actual AI classification.
504 The Bedrock call didn't finish before its deadline-derived timeout (see Special behaviors). Yes, with backoff — likely transient.
429 Bedrock throttled the request. Yes, with backoff.
502 Bedrock returned a 5xx, or the connection to it failed outright. Yes, with backoff.
500 An unexpected bug in this Lambda, unrelated to the request or Bedrock. Retry cautiously; if it persists, this needs investigation, not a retry loop.

Special behaviors

Idempotency

This service does not read or enforce the Idempotency-Key header — send one by platform convention if you like, but it's ignored. There is also no natural request-id field to de-dupe on instead.

This isn't an oversight so much as a scope mismatch: this Lambda has no persistence of its own (no database writes, no queue emission) — it's a pure request → response transform. "Idempotency" in the usual create/update-a-record sense doesn't apply here, because there's no record being created.

What actually happens on a repeat call: there's a per-container, in-memory cache (500s TTL, 500-entry LRU bound) keyed on the exact (channel, subject, message, extras) tuple. An identical repeat that lands on the same warm Lambda container within 500 seconds gets served the cached classification (ai_result.cached: true) without a second Bedrock call. A repeat that lands on a different container, or arrives after the TTL, just runs again — normally, possibly with a slightly different ai_summary wording since the model isn't deterministic. This is a cost-saving convenience for a same-container retry, not a durable or cross-container de-dupe guarantee.

Deadline-derived timeout

The Bedrock call is bounded by whatever time is actually left on the Lambda invocation, not a fixed constant — this is what lets a slow model response come back as a clean 504 instead of the connection just hanging until API Gateway's own timeout kills it with nothing written back.

Deterministic field normalization

These four are never left to model judgment — they're filled or corrected by code, after the model responds:

FieldRule
messageAlways the channel's own cleaned input text, verbatim — never rewritten or summarized by the model.
noted_byAlways the resolved channel name (e.g. "email") — never model-authored.
mobileIf the model's extracted digits-only value is exactly 10 digits (no country code), 91 is prefixed automatically. Any other length is left as-is.
website_urlIf the model found nothing stated explicitly in the request text, this falls back to the sender's own email domain (from from_email/from/reply_to) — unless that domain is a free/consumer email provider (Gmail, Yahoo, Outlook, etc.), in which case it's left blank rather than guessed.
emailIf still blank after everything above, defaults to noreply@vidyaone.com in the final response. This fallback is applied last, after the "no contact info found" warning below is already computed — so that warning still reflects whether a real email/mobile was actually found.

Contact-info warning

If the model finds neither an email nor a mobile number anywhere in the request, ai_result.warnings includes a note that there's no way to contact the requester back. This is non-fatal — the response is still a normal 200, just flagged for visibility.

Bot / spam / prompt-injection content

Not rejected outright — the model is instructed to classify clearly spam, bot-scripted, abusive, or prompt-injection content as form_type: "other" rather than force-fitting it into a real category. Request text is always treated as untrusted data, never as instructions to the model.

Pagination / batching / async side effects

None of these apply — one call classifies exactly one submission synchronously, and this service emits no queue message or event of any kind.
