vWebsite-AdminAPI — Developer Guide

Documents the DataJson, Module, Page, Onboard, and Plugin resources.

Postman setup guide

  1. Use Postman for web (web.postman.co), not the desktop app.
  2. Install the Postman Interceptor Chrome extension — it lets Postman's web app read cookies from your Chrome session.
  3. Enable Interceptor, then log into the product normally in Chrome. Once logged in, your session is available to Postman automatically — you don't need to set any auth header or cookie by hand.
  4. Download the collection from the link in the navbar above and import it into Postman, then send requests — it's pre-configured for Testing.

Common request & response rules

Authentication

Authentication required on every route documented in this guide.

Headers required on every request

Content-Type: application/jsonwrites onlyRequired on any request that carries a body.
Idempotency-Keymutating requestsA UUID the caller generates per request. Required on every POST and PUT below. See the Idempotency line under each endpoint for what happens if you resend the same key/body.

Common query parameter

NameTypeRequiredNotes

Response envelope

Every response — success or failure — uses the same JSON shape:

{
  "success": true | false,
  "message": "human-readable string" | null,
  "errors":  [ { "code": "...", "message": "...", "field": "..." } ] | null,
  "data":    { ... } | [ ... ] | true | null
}

Success example:

{ "success": true, "message": null, "errors": null, "data": true }

Error example:

{
  "success": false,
  "message": "Validation failed.",
  "errors": [ { "code": "VALIDATION_FAILED", "message": "Inst ID must be greater than 0.", "field": "InstSaaSId" } ],
  "data": null
}

Each entry in errors[] has a machine-readable code — switch on code, not on message text.

DataJson

Reads and writes one tenant-scoped JSON configuration file. A successful POST also flags the institution's site as having unpublished changes.

GET /data

Fetch the parsed contents of one JSON config file for the caller's institution. Call it to load a saved document before editing.

Request

EnvironmentURL
TestingGET https://api-vweb.vidyaone.com/test/admin/data?product={product}&file={file}
ProductionGET https://api-vweb.vidyaone.com/admin/data?product={product}&file={file}

Sample request

GET /data?product=vweb
    &file=data_home.json   // required, string, matches ^(data_|config_|plugin_)[A-Za-z0-9_-]+\.json$, max 255 chars

Response — 200 OK

data is the file's JSON content verbatim (object or array).

{
  "success": true,
  "message": null,
  "errors": null,
  "data": { "hero": { "title": "Welcome" }, "sections": [ ] }
}

Error responses

StatuscodeCause
400VALIDATION_FAILEDfile empty, or institution not resolved.
400INVALID_INPUTfile fails the naming pattern, a path-traversal attempt is detected, the stored file is empty or exceeds 10 MB, or the stored content is not valid JSON.
400REQUIRED_FIELDproduct missing.
401UNAUTHORIZEDAuthentication required.
404RECORD_NOT_FOUNDNo such file exists for this institution.
502EXTERNAL_SERVICE_ERRORThe file storage backend denied access, failed, or did not answer within 10 seconds.
POST /data

Create or overwrite one JSON config file for the caller's institution, and (optionally) get presigned upload URLs for binary assets referenced by that file. Call it whenever the customer saves site data.

Request

EnvironmentURL
TestingPOST https://api-vweb.vidyaone.com/test/admin/data?product={product}
ProductionPOST https://api-vweb.vidyaone.com/admin/data?product={product}

Headers: Content-Type: application/json, Idempotency-Key.

Sample request

POST /data?product=vweb
{
  "file": "data_home.json",                 // required, string, matches ^(data_|config_|plugin_)[A-Za-z0-9_-]+\.json$, max 255 chars — must not be a system-generated file (see 403 below)
  "data": {                                  // required, JSON object or array — max nesting depth 20, max 1000 keys per object, max 10000 items per array, serialized size ≤ 10 MB
    "hero": { "title": "Welcome", "image": "hero.png" },
    "sections": [ { "type": "text", "body": "About us" } ]
  },
  "upload_files": [                          // optional, array of objects, max 20 items
    { "file_name": "hero.png" }               // required per item, string, max 200 chars, extension in jpg/jpeg/png/gif/webp/bmp/pdf/txt/csv/xlsx/xls/docx/doc, no path separators, "..", control or dangerous characters, no executable/script extension anywhere in the name
  ]
}

Response — 200 OK

{
  "success": true,
  "message": null,
  "errors": null,
  "data": {
    "message": "File uploaded successfully",
    "file_key": "<internal storage path>",
    "size": 412,
    "upload_presign": {                       // present only when upload_files was sent
      "uploads": [
        {
          "fileName": "hero.png",
          "key": "<internal storage path>",
          "post": { "url": "...", "fields": { "key": "...", "policy": "...", "x-amz-signature": "..." } },
          "expiresIn": 120,
          "maxFileSize": 10485760,
          "contentTypePrefix": "image/"
        }
      ],
      "rejected": [
        { "fileName": "notes.exe", "reason": "Unsupported file type for a file upload." }
      ]
    }
  }
}

Per-file presign problems go into rejected[] (reasons: missing_file_name for an empty name, unsupported_file_type, presign_generation_failed, or a validation message) — they do not fail the request. Presigned upload URLs expire after 120 s and cap the upload at 10 MB. Uploading a file with the same name again replaces the earlier upload.

Error responses

StatuscodeCause
400VALIDATION_FAILEDfile empty, data is not an object/array, upload_files has more than 20 items, an upload_files item has no file_name, the body is malformed, or institution not resolved.
400INVALID_INPUTfile fails the naming pattern or a path-traversal/shell-character check, data exceeds the depth/key/array limits, or the serialized payload exceeds 10 MB.
400REQUIRED_FIELDproduct missing.
401UNAUTHORIZEDAuthentication required.
403FORBIDDENfile is a system-generated file: config_active_page.json, config_active_plugin.json, plugin_notice.json or plugin_announcement.json (any letter case). These can be read with GET /data but not written.
502EXTERNAL_SERVICE_ERRORThe file storage backend rejected the write, failed, or did not answer within 10 seconds.

Idempotency. Sending the same Idempotency-Key and body again overwrites the same file with identical bytes and returns 200 OK with the same file_key — same final state, not a new record. When upload_files is sent, each call mints fresh presigned upload URLs regardless.

Side effect. After a successful save, the institution's site is flagged as having unpublished changes. If that flag update fails, this request still returns 200 OK (the file is already saved).

Manages per-institution feature modules. websiteDisplay decides whether a module is shown on the website. Module names are matched exactly (case-sensitive, not trimmed) against the catalog — use the names from GET /module/list-pages as-is.

{

GET /module/limit

Get the module limit from the caller's institution's current plan — the maximum number of modules that can have websiteDisplay: true at once. Call it to validate the module-settings screen before saving.

Request

EnvironmentURL
TestingGET https://api-vweb.vidyaone.com/test/admin/module/limit?product={product}
ProductionGET https://api-vweb.vidyaone.com/admin/module/limit?product={product}

Sample request

GET /module/limit?product=vweb

Response — 200 OK

{ "success": true, "message": null, "errors": null, "data": { "enableModule": 10, "enabledCount": 7 } }

enableModule is resolved the same way POST /module enforces it: -2 = unlimited, a positive number = max modules with websiteDisplay: true, 0 = none may be enabled (a plan with no value or any other negative value comes back as 0). enabledCount = the institution's modules currently with websiteDisplay: true — enableModule - enabledCount is how many more can be turned on.

400REQUIRED_FIELDproduct missing.

404RECORD_NOT_FOUNDThe institution is inactive or does not exist ("Institution not found."), or its plan row does not exist ("Plan not found.").

POST /module

Bulk create-or-update module websiteDisplay values for the caller's institution in one call. Call it when the customer saves the module-settings screen.

Request

EnvironmentURL
TestingPOST https://api-vweb.vidyaone.com/test/admin/module?product={product}
ProductionPOST https://api-vweb.vidyaone.com/admin/module?product={product}

Headers: Content-Type: application/json, Idempotency-Key.

Sample request

POST /module?product=vweb
[                                                              // required, non-empty array, max 100 items
  { "moduleName": "data_home",        "websiteDisplay": true },  // moduleName: required, string, non-empty, exact catalog name (see GET /module/list-pages)
  { "moduleName": "data_school_info", "websiteDisplay": true }   // websiteDisplay: required, boolean — no default; missing or null fails the request
]

data_home and data_school_info are mandatory modules — their websiteDisplay is always saved as true regardless of what's sent.

Behaviour

  • Per item: the institution's row for that module is updated (a deleted or inactive row is revived/reactivated) only if something differs; if it has no row yet, one is created. A module never gets a second row.
  • The whole batch is saved in one transaction.
  • Duplicate names within the same payload — the last occurrence wins.
  • Every moduleName must be a recognized module (see GET /module/list-pages) — an unrecognized name fails the whole batch before anything is saved.
  • The institution must be active and have a plan row — otherwise the whole request fails before anything is saved.
  • Plan module limit (see GET /module/limit): only modules with websiteDisplay: true count. The request fails before anything is saved only if it would raise the number of enabled modules and leave it above the limit, so an institution already over its limit (e.g. after a plan downgrade) can still turn modules off. Concurrent saves for the same institution are serialised.
  • A module saved with websiteDisplay: false also turns off every page of that module for the institution (see Page).

Response — 200 OK

{ "success": true, "message": null, "errors": null, "data": true }

Error responses

StatuscodeCause
400VALIDATION_FAILEDBody missing, malformed or not a JSON array; empty array; more than 100 items; a null item; an item with empty moduleName or without websiteDisplay; or institution/caller not resolved.
400INVALID_INPUTA submitted value fails a database check constraint.
400REQUIRED_FIELDproduct missing, or a required database column was left null.
400LIMIT_EXCEEDEDSaving this batch would raise the number of modules with websiteDisplay: true above the plan limit — message "Module limit exceeded. Max allowed: {n}."
401UNAUTHORIZEDAuthentication required.
404RECORD_NOT_FOUNDA moduleName is not in the active module catalog, the institution is inactive or does not exist, or its plan row does not exist.
409DUPLICATE_RECORDUnique conflict on the module for this institution.
409FOREIGN_KEY_VIOLATIONA referenced record does not exist.

Idempotency. Sending the same Idempotency-Key and body again leaves exactly one row per module in the same final state and returns 200 OK data: true; the repeat changes nothing, so it sets no flags and fires no event. The response does not distinguish created from updated rows.

Side effect. When the save changed anything, the institution's module-setup onboarding step (see GET /onboard/module) is marked complete and the site is flagged as having unpublished changes. When pages were turned off with a module, the institution's active-pages file is rebuilt. If any of these fails, this request still returns 200 OK (the modules are already saved).

Events

Fires MODULE_STATUS_UPDATED after the save, only when at least one module was created or changed, or pages were turned off with a module.

    "pluginCode": "vweb_notice" // required, string, non-empty, max 50 chars — trimmed, matched case-insensitively

Behaviour

  • pluginCode must be an active catalog plugin of the calling product (a test- prefix is ignored for this match).
  • Not yet added: a free plugin is added; a paid plugin starts its trial — a paid plugin with no trial is refused.
  • Already added, free: the plugin is added back if it had been removed; its websiteDisplay is kept.
  • Already added, paid: a running trial is left unchanged (200 OK); a purchased plugin is refused; an expired trial or plan is refused.
  • A newly added plugin starts with websiteDisplay: false — call PUT /plugin/websitedisplay to show it.

{ "success": true, "message": null, "errors": null, "data": true }
