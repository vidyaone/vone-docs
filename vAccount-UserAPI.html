vAccount-UserAPI

Internal "SaaS user" lookup & profile API — resolves a signed-in user's institute / plan / subscription status, and reads & updates the user's own profile and social links. Read-only against Postgres views, plus a single write path for the profile.

01 Overview

This service is consumed by other VIDYAOne front-ends / BFF layers on behalf of a signed-in user. It has two groups of routes:

  • /saas/* — resolve the caller's institute, product, plan, support tier, org and subscription remaining days for the current SaaS context.
  • /user/* — read the caller's editable profile (incl. social links) and write it back.
The /internal/* routes (service-to-service user validation) are not covered here — they are reachable only from private Lambdas inside AWS and are not part of the developer-facing contract.

03 Authentication

Every route documented here is behind the vAccount SaaS cookie. Only /internal/* is exempt. There is no API key, bearer token or query-string auth.

  • The cookie is an HttpOnly, signed session cookie issued by the vAccount login flow. Its signing key is resolved at runtime from Secrets/DynamoDB (DynamoDb:CookieConfigKey).
  • Browser callers: send the request with credentials (fetch(url, {credentials:'include'}) / XMLHttpRequest.withCredentials = true). The cookie rides along automatically.
  • Server-to-server callers: forward the end user's Cookie header verbatim.
  • Two payload shapes are decoded from the same cookie by controller filters:
    • SaaSPayload used by GET /saas/userinstdetail — carries InstId, ProductId, ServiceMode, InstSaaSCode, TestMode, UserId. Requires a cookie minted inside a specific institute/product context.
    • AccountPayload used by GET /saas/userdetail, GET /user/edit, PUT /user — carries UserId and TestMode.
  • A missing / expired / invalid cookie is rejected by the SaaS-cookie middleware before the action runs (see §08).
  • CORS / preflight: OPTIONS is short-circuited with 200 before auth runs. Actual Access-Control-Allow-* headers are emitted by the shared vOne.Utilities pipeline — confirm the allowed origin list with the platform team; cross-origin browser calls must be credentialed.

Special behaviour — renew redirect

When remainingDays ≤ 0 and isFree == false, the endpoint does not return JSON. It returns:

302 FOUND

Location: https://test-account.vidyaone.com/renew?saascode=<instSaaSCode>   # when cookie TestMode = true
Location: https://account.vidyaone.com/renew?saascode=<instSaaSCode>        # when cookie TestMode = false

Browser clients following redirects will land on the renew page. Programmatic clients should treat a 302 to /renew as "subscription expired".

09 Social links — reconcile behaviour

putDTO.socialLinks is treated as the desired full set of the caller's links. Model: one link per platform per user.

Payload itemEffect
socialLinkId: 0, new platformInsert a new link.
socialLinkId: 0, platform already existsUpdates the existing link for that platform (idempotent — safe to resend).
socialLinkId: > 0Updates that link. If the id is not one of the caller's active links → 404, nothing is changed.
an existing active link whose id/platform is absent from the arraySoft-deleted (is_deleted = true).
socialLinks omitted or nullLinks left untouched.
socialLinks: []All of the caller's links are soft-deleted.
same platform twice in the array400 — request rejected, nothing changed.

Worked example

Caller currently has: #7 LinkedIn → /old, #8 GitHub → /gh, #9 Twitter → /tw.

PUT /user
{
  "putDTO": {
    "fullName": "Asha Rao",
    "socialLinks": [
      { "socialLinkId": 7, "platform": "LinkedIn", "profileUrl": "https://linkedin.com/in/asha" },
      { "socialLinkId": 0, "platform": "YouTube",  "profileUrl": "https://youtube.com/@asha" },
      { "socialLinkId": 0, "platform": "github",   "profileUrl": "https://github.com/asha-new" }
    ]
  }
}

Result:

  • #7 LinkedIn → updated to /in/asha.
  • YouTube → inserted (new platform).
  • #8 GitHub → updated to /asha-new (the socialLinkId:0 item matched the existing github platform, case-insensitive).
  • #9 Twitter → soft-deleted (absent from the array).

10 Response envelope

All JSON responses use the shared vOne.Utilities envelope. Payloads are camelCase.

{
  "success":    true | false,
  "statusCode": 200,
  "message":    "",            // human string; may be empty on success
  "data":       { /* payload */ },  // the DTO, or null
  "errors":     null          // list/map of error detail on failure, else null
}
  • On success: success = true, data holds the DTO (or null for PUT /user), errors = null.
  • On failure: success = false, message describes the error, errors carries detail (e.g. per-field validation messages), data is null. The failure envelope is produced centrally by the exception middleware.
  • The 302 renew redirect (§5) has no JSON body — just a Location header.

11 Status codes

CodeWhenBodyRetry?
200 Success. Envelope with data (GET) or message only (PUT /user). —
302 GET /saas/userinstdetail only — paid plan lapsed (remainingDays ≤ 0 && !isFree). No body; Location: …/renew?saascode=…. No — send the user to renew.
400 Validation failure (PUT /user): bad/missing fullName, malformed email/mobile/URL, dob not in the past, socialLinks > 50, duplicate platform, missing putDTO / malformed JSON. Failure envelope; errors lists the field messages. No — fix the payload.
401 Missing / expired / invalid SaaS cookie, or wrong payload scope for the route. Failure envelope (or middleware challenge). Re-authenticate, then retry.
404 No profile row for the caller (GET /user/edit, PUT /user); SaaS/institute row not found for the context (/saas/*); a socialLinkId > 0 that isn't the caller's. Failure envelope, message = "… not found". No.
409 PUT /user — write conflict: concurrent modification, or a uniqueness violation on social links. Failure envelope. Yes — re-GET and retry once.
500 Unhandled error (DB unavailable, etc.). Failure envelope; detail suppressed outside dev. Yes — with backoff.

Exact codes are assigned by the shared vOne.Utilities exception middleware; the mapping above reflects its conventional behaviour for the exception types this service throws.

13 Limits & behaviour

  • Idempotency. PUT /user is safe to retry — re-sending the same body converges to the same state (profile is overwritten wholesale; links are matched by id, then by platform).
  • Write atomicity. The profile row and the social-link changes are committed in one DB transaction. In a rare mid-commit infra failure the client gets 500/409; retry the same request.
  • Ownership. Every read/write is scoped to the cookie's UserId. You cannot read or mutate another user's profile or links; a foreign socialLinkId yields 404.
  • Soft delete. Removed social links are flagged is_deleted = true, not hard deleted; they never reappear in GET /user/edit.
  • Limits. socialLinks ≤ 50 per request; platform unique per user. Field length caps as per §8. No request-rate limiting in this service (API Gateway may impose its own).
  • No pagination. No list endpoints; nothing is paged.
  • No bot / spam filtering. Not applicable — all routes are cookie-authenticated.
  • No async side effects / events. This service does not publish to SQS/SNS or emit any message. Writes touch only tbl_user_info and tbl_user_social_links; there is nothing downstream for a consumer to observe.
  • First-time profile. PUT /user updates an existing tbl_user_info row; if the caller has no row yet it returns 404 (the row is expected to be provisioned by the account/signup flow).
  • token field. The token in /saas/* responses is a fresh random 256-bit Base64Url value per call — opaque, for the caller to hand on; it is not a session or bearer token issued by this service.
