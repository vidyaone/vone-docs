1. What it does

Consumes enriched form-submission messages from an SQS queue (produced by vone-form-post-lambda). For every SQS record it:

  1. Parses and structurally validates the message body into a typed SubmissionEvent.
  2. Normalizes mobile / whatsapp fields inside formFields to numeric strings.
  3. Geo-enriches location from sourceIp via ip-api.com (non-fatal).
  4. Resolves a prefix for the formType from config.
  5. Writes the submission to DynamoDB table vone-form-data with a conditional (idempotent) put.
  6. POSTs the submission to a Zoho Flow incoming webhook. This step is fatal — a failure returns the record to SQS.

An SES email step exists in the code but is currently commented out (see §10). Partial-batch failure reporting is used so only failed / deferred records are retried.

There is no HTTP endpoint, no API Gateway, and therefore no request method, content-type, CORS, or auth on the invocation. Auth to the one outbound dependency (Zoho Flow) is the zapikey embedded in the webhook URL.

2. Entry point & trigger

Invoked by the Lambda SQS poller with a standard SQS event. The event source mapping must have ReportBatchItemFailures enabled — the handler returns batchItemFailures and relies on SQS to re-drive only the listed messages. 

{
  "Records": [
    {
      "messageId": "d5f9…",          // used as fallback requestId and as the failure identifier
      "eventSource": "aws:sqs",       // REQUIRED — any other value ⇒ record discarded
      "body": "{ …JSON string… }",    // the submission payload, see §3
      "attributes": { … },            // ignored
      "messageAttributes": { … }      // ignored
    }
  ]
}

Only messageId, eventSource and body are read. Message attributes set by the publisher are not consumed here.

3. Input message contract

Records[].body is a JSON string; parsed it must be a JSON object with the fields below. Shape mirrors publish_helper._build_message() in vone-form-post-lambda.

FieldTypeRequiredRules / handling
formTypestringYes Trimmed and lower-cased. Empty or missing ⇒ ParseError ⇒ record discarded (not retried).
formFieldsobjectYes Must be a JSON object. Any other type ⇒ ParseError ⇒ discarded. Arbitrary keys allowed; values pass through except phone normalization (§5) and float→Decimal on the DynamoDB copy.
requestIdstringNo If absent or falsy, falls back to the SQS messageId. Stored as-is; also used in the REQUEST# dedup key when no idempotency key is present.
idempotencyKeystringNo Client GUID passed through by the ingest lambda. Empty string when the client opted out (Idempotency-Key: none). Absent on older queued messages. Drives dedup (§7).
subjectstringNo Trimmed, then capped to 500 chars.
pageUrlstringNo Trimmed, then capped to 1000 chars.
submittedAtstring (ISO-8601)No Lenient parse; trailing Z accepted. Unparseable or missing ⇒ now(UTC). A value with no offset is kept as-is (naive).
deviceobjectNo Read keys: userAgent (≤500), browser (def. "Unknown"), os (def. "Unknown"), deviceType (def. "unknown"), isMobile (bool, def. false). Missing block ⇒ defaults.
locationobjectNo Read keys: sourceIp (≤45), plus optional pre-filled geo keys countryCode / countryName / region / city / timezone. If countryCode is already set, geo lookup is skipped.
botDetectionobjectNo Read keys: isBot (bool, def. false), reasons (list, or a bare string kept whole; any other type ⇒ empty). Stored and forwarded; never causes rejection.

A message that is valid JSON but the wrong shape (e.g. location sent as a string) raises ParseError and is discarded. Only unexpected/transient errors (bugs, throttling, DynamoDB / webhook failures) are returned to SQS for retry.

5. Phone-field normalization

Applies to formFields keys mobile and whatsapp (case-insensitive, trimmed key match). Runs before the record is stored or forwarded, so DynamoDB and the webhook see the normalized value. Never raises.

StepRule
1Skip if value is None, a bool, or a non-integer float.
2Integer-valued numbers use their exact integer form (no ".0").
3Strip every non-digit character.
4Drop leading zero(s).
5Exactly 10 digits ⇒ prefix 91 ⇒ 12-digit string.
6Any other length (incl. already 12) ⇒ kept as the stripped digit string, no prefix.
7No digits at all / all zeros ⇒ field left untouched.
8When a value is processed it is always written back as a string — the field type is consistent across submissions.

User-Agent: vone-form-consumer-lambda/1.0

On successlocation filled: countryCode (≤10), countryName (≤100), region (≤100), city (≤100), timezone (≤60)
On any failurenon-fatal — logged as [WARN], record proceeds with location unchanged
Cacheper-container, successes only, keyed by IP, max 2000 entries, FIFO eviction
Rate limitip-api free tier ≈ 45 req/min; over that ip-api returns an error and the lookup is skipped (non-fatal)

7. Idempotency & de-duplication

The DynamoDB write is a conditional put keyed on:

pkFORM#<FORMTYPE> — form_type upper-cased
skIDEMPOTENCY#<idempotencyKey> when the key is present
REQUEST#<requestId> when the client opted out (blank key)
Conditionattribute_not_exists(pk) AND attribute_not_exists(sk)
  • Fresh write ⇒ is_new = true ⇒ webhook fires.
  • ConditionalCheckFailedException ⇒ duplicate ⇒ is_new = false, no error. The webhook then fires only if the existing record's zohoFlowSync is still false (i.e. a prior attempt never confirmed delivery).
  • Re-using one idempotencyKey across separate ingest POSTs (each with its own requestId) collapses to a single stored record and a single webhook delivery.
  • SQS at-least-once redelivery of the same message is absorbed by the same condition.

Delivery to Zoho is best-effort exactly-once, not guaranteed exactly-once: a crash between a successful POST and the zohoFlowSync=true marker, or an independent SQS redelivery in that window, can produce a duplicate POST. Consumers should de-dupe on requestId.

10. Email (SES) — disabled

notification_helper.py, SES_SENDER_EMAIL and the 21-entry FORM_TYPE_EMAILS map are all still present, but the notify.send_email(evt) call in the handler is commented out — no email is sent for any submission today.

When re-enabled it would: send one HTML + plain-text email via SES per form_type, to FORM_TYPE_EMAILS[formType].recipients, from FORM_TYPE_EMAILS[formType].sender (fallback SES_SENDER_EMAIL), only on a fresh save, and non-fatally (SES failure is logged, not retried). Subject format:

{prefix}#v#{reply_to_email}#e#{requestId}#r#{product}#p#{subject}
e.g.  COMPLAINT#v#ankit@example.com#e#550e8400-…#r#ExamModule#p#complaint from ankit

reply_to_email = formFields.email if it looks like an email, else blank. product = formFields.product if present, else blank.

11. Partial-batch failure & retry

The handler returns:

{ "batchItemFailures": [ { "itemIdentifier": "<messageId>" }, … ] }
Per-record outcomeIn batchItemFailures?
processed OK (saved + webhook 2xx, or duplicate already synced)no
ParseError (malformed / wrong-shape message)no — discarded, logged [ERROR] Parse error — discarding
webhook failure, DynamoDB error, or any unexpected exceptionyes — SQS re-drives that message; after maxReceiveCount it goes to the DLQ
deferred for time budget (§12)yes

Requires FunctionResponseTypes = ["ReportBatchItemFailures"] on the event source mapping, otherwise SQS retries the whole batch on any thrown error.

12. Time-budget deferral

Before starting each record the handler checks context.get_remaining_time_in_millis(). If it is below config.LAMBDA_MIN_REMAINING_MS (10 000 ms), the current record and every remaining record in the batch are added to batchItemFailures and the loop stops: 

[WARN] Time budget low (8200ms) — deferring 4 record(s) to SQS retry | request_id=…

This prevents a mid-record Lambda timeout that would otherwise reprocess work whose side effects (DynamoDB write, webhook POST) already ran. It is a heuristic, not a guarantee — set a comfortable function timeout and a modest SQS BatchSize.

LimitTriggerEffect
DynamoDB — 380 KB (_MAX_FIELDS_BYTES) serialized formFields exceeds it stored formFields = {"_truncated": "…"}, status = "SAVED_TRUNCATED". The webhook still receives the full form_fields (subject to its own cap).
Webhook — 256 KB (ZOHO_FLOW_WEBHOOK_MAX_BODY_BYTES) serialized POST body exceeds it POST body's form_fields replaced with {"_truncated": "…full submission in DynamoDB"}; DynamoDB copy is unaffected.
