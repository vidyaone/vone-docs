1. Overview

This microservice manages institutes and the organizations that own them, tracks an institute's onboarding status, and exposes two shared reference-data lookups (institute types, organization types).

ControllerRoute prefixAuth filterPurpose
InstituteController/ (empty)[AccountPayload]Create / read / update / deactivate / soft-delete / re-parent a user's institutes
InstituteTypeController/insttype[AccountPayload]Global institute-type reference data (read-only)
OrganizationTypeController/orgtype[AccountPayload]Global organization-type reference data (read-only)
OrganizationController/org[AccountPayload]Create / read / update / deactivate / soft-delete a user's organizations, plus KYC
OnboardController/onboard[SaaSPayload]Read / set an institute's onboarding-complete status
TempController/tempnoneInternal / temporary plan-change route (see §11)
  • Auth model: Institute / InstituteType / OrganizationType / Organization use the account cookie (vacc-account-auth). Onboard uses the product SaaS cookie (vacc-<product>-auth). Both also require the product query parameter. See §2.
  • CORS & OPTIONS: CORS is handled at AWS API Gateway. Pre-flight OPTIONS is answered 200 in-app before auth runs.
  • Every response — success or failure — uses the same JSON envelope. See §3.
  • Reference data (institute/org types) is not user-scoped; institute and organization data is always scoped to the authenticated user (creatorUserId = cookie UserId).
  • Numbers may arrive as JSON strings. The API is configured with JsonNumberHandling.AllowReadingFromString, so "instTypeId": "3" is accepted as well as "instTypeId": 3.

2. Authentication & common request rules

The Institute, InstituteType, OrganizationType and Organization controllers are protected by the [AccountPayload] filter. The Onboard controller uses [SaaSPayload] instead — same product rule, a different cookie, and an institute context (see §10). The Temp controller has no auth filter (see §11).

[AccountPayload] on each request:

  1. Reads the product value from the query string. If missing/blank → 400 with code REQUIRED_FIELD.
  2. Strips a leading test- from the product (e.g. test-lms → lms) and, if present, marks the request test mode (§12.1).
  3. Resolves the account auth cookie for that product. If missing/expired/invalid → 401 with code UNAUTHORIZED.
  4. Exposes the caller's UserId to the handler. All institute/organization reads and writes are scoped to this UserId; it is never trusted from the request body.

Required on every request

WhereNameRequiredNotes
Query stringproductyesCalling product identifier, e.g. lms. Prefix with test- for test mode. Required by the auth filter on every route, including the GET lookups. Also read by the Temp route even though it has no auth.
HeaderCookie: vacc-account-auth=<token>yesSent automatically by the browser for *.vidyaone.com. For curl, pass it explicitly. Onboard needs vacc-<product>-auth instead.
HeaderContent-Type: application/jsonwrites onlyRequired for POST/PUT/DELETE requests that carry a body.
There is no bearer token and no custom auth header. Identity comes entirely from a cookie plus the product query parameter. For Institute / InstituteType / OrganizationType / Organization that cookie is vacc-account-auth; for the Onboard controller (§10) it is the product SaaS cookie vacc-<product>-auth (e.g. vacc-lms-auth), which also carries the institute context (InstId, UserId).

3. Response envelope & error codes

Every response uses the same JSON envelope with four top-level keys:

{
  "success": true | false,
  "message": "human-readable string" | null,
  "errors":  [ { "code": "...", "message": "...", "field": "..." } ] | null,
  "data":    { ... } | [ ... ] | null
}
  • Command success (POST/PUT/DELETE): { "success": true, "message": "<text>", "errors": null, "data": null }.
  • Query success (GET): { "success": true, "message": null, "errors": null, "data": <payload> }.
  • Failure: success is false, message describes the error, errors holds detail entries (or null), data is null.
  • Error bodies emitted by the exception middleware are serialized camelCase and omit null fields; success bodies emitted by the controllers include the null fields explicitly. Treat any absent key as null.
  • Each entry in errors[] has a machine-readable code — switch on code, not message. field is present for validation / required-field errors.

Retry guidance: 400/401/404/409 are terminal — fix the request. 500 may be retried with backoff; the DB layer already retries transient faults 3× internally (EnableRetryOnFailure(3)). 499 means the caller went away — nothing to retry server-side.

6. Institute controller

Route prefix / (empty) — every path in this section is relative to the base URL. All endpoints are [AccountPayload]-protected and scoped to the authenticated user (creatorUserId = cookie UserId). Writes match rows by instId and creatorUserId; a row that does not match returns 404. Soft-deleted institutes (isDeleted = true) are excluded from every read.

10. Onboard controller

Tracks whether an institute has finished onboarding. Route prefix /onboard. Three endpoints, none of which take a request body — every input comes from the cookie and the product query parameter.

12. Special behaviours

12.1 Test mode

Prefix the product value with test- (e.g. ?product=test-lms) to run the request in test mode. The prefix is stripped before the product is resolved; the flag is carried through to the handlers and, for GET /listbyuser, baked into each adminUrl. Use the same base URL — test mode is a property of the request, not a separate host. (This is distinct from the /test/ segment in the Testing environment base URL.)

12.2 Per-user organization cap

POST /org rejects creation with 400 ("You can create a maximum of 3 organizations.") once the caller owns 3 non-deleted organizations. Deactivated orgs still count; soft-deleted orgs do not. The cap is enforced in application code, so a burst of concurrent POSTs from one user can momentarily exceed it. There is no equivalent cap on institutes.

12.3 Exactly one default per user (organizations)

Setting a default always clears it elsewhere, in one transaction. Three equivalent ways:

  • PUT /org/default with { "orgId": N }.
  • POST /org with postDTO.isDefault = true — the swap runs immediately after the insert.
  • PUT /org with putDTO.isDefault = true — the swap runs inside the update transaction.

isDefault = false on POST/PUT is a no-op for the default flag — it does not clear an existing default. You move the default by promoting another org. If a user has never set a default, none of their orgs is default — there is no automatic "first org becomes default".

12.4 KYC upsert (organizations)

POST /org inserts the KYC row in the same unit of work as the org insert. On PUT /org: when putDTO.kyc is present, an existing tbl_organization_kyc row is updated in place (and un-deleted if it had been soft-deleted); otherwise a new row is inserted and linked. The KYC write shares the org update's transaction — if either part fails, neither is applied.

12.5 Soft-delete / deactivate visibility

Applies to both institutes and organizations (the org-only "cap" column is noted).

12.6 Full write / no partial merge

PUT / (institute) and PUT /org overwrite every writable column with the value in the payload. Optional string fields default to "" when omitted, which clears the column. Always load the current row with GET /edit / GET /org/edit, mutate it, and send the whole object back. Institute PUT does not touch plan / product.

12.7 Downstream side effects

  • POST / (create institute) synchronously invokes the client first-setup Lambda (vweb-client-first-setup-lambda, InvocationType = RequestResponse) only when the resolved product subdomain contains -website. On success, for the same -website case it then calls the vWebsite template service to write trial-plan data into the client's template.json. For non--website products (e.g. lms, account) no Lambda is invoked. A failure in either step surfaces as 500; the institute row may already be committed.
  • Onboard endpoints only flip flags on tbl_onboard — no Lambda, no queue.
  • SQS. A notification queue is configured (Sqs:NotificationQueueUrl → vacc-notification-sender-queue in ap-south-1) and an ISqsService is registered, but no active handler in this service publishes to it — the trial-start / deactivate / plan-change SQS producers exist only in disabled (x_-prefixed) code. When it is re-enabled, messages are sent as camelCase JSON bodies with a single message attribute EventType (String). Consumers should not rely on it today.

12.8 Pagination quirk

GET /listbyuser (institutes) requires pageNumber and pageSize (both > 0) — it passes them straight to a validator that rejects 0. Every other list endpoint (/org/listbyuser, /insttype/list, /orgtype/list) treats them as optional and falls back to defaults (page 1; size 50 for orgs, 10 for the type lookups), and caps pageSize at 200.
