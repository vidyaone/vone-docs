1. Overview

This service manages organizations owned by a user, tracks an institute's onboarding status, and exposes two shared reference-data lookups (institute types and organization types). All routes documented here live on four controllers:

ControllerRoute prefixPurposeEndpoints
InstituteTypeController/insttypeGlobal institute-type reference data (read-only)GET list, GET options
OrganizationTypeController/orgtypeGlobal organization-type reference data (read-only)GET list, GET options
OrganizationController/orgCreate / read / update / deactivate / soft-delete a user's organizations, plus KYC9 endpoints (see §7)
OnboardController/onboardRead / set an institute's onboarding-complete status3 endpoints (see §8)
  • Auth model: the InstituteType / OrganizationType / Organization controllers use the account cookie (vacc-account-auth); the Onboard controller uses the product SaaS cookie (vacc-<product>-auth). Both also require the product query parameter. See §2 and §8.
  • CORS & OPTIONS: handled at AWS API Gateway. Pre-flight OPTIONS is answered 200 before auth runs.
  • Every response — success or failure — uses the same JSON envelope. See §3.
  • Reference data (institute/org types) is not user-scoped; organization data is always scoped to the authenticated user.

2. Authentication & common request rules

The InstituteType, OrganizationType and Organization controllers are protected by the [AccountPayload] filter. The Onboard controller uses the [SaaSPayload] filter instead — same product rule, but a different cookie and an institute context; see §8. [AccountPayload] on each request:

  1. Reads the product value from the query string. If missing/blank → 400 with code REQUIRED_FIELD.
  2. Strips a leading test- from the product (e.g. test-lms → lms) and, if present, marks the request test mode.
  3. Resolves the account auth cookie for that product. If missing/expired/invalid → 401 with code UNAUTHORIZED.
  4. Exposes the caller's UserId to the handler. All organization reads/writes are scoped to this UserId; it is never taken from the request body.

Required on every request

WhereNameRequiredNotes
Query stringproductyesCalling product identifier, e.g. lms. Prefix with test- to hit test mode. Required by the auth filter on every route, including the GET lookups.
HeaderCookie: vacc-account-auth=<token>yesSent automatically by the browser for *.vidyaone.com. For curl, pass it explicitly.
HeaderContent-Type: application/jsonwrites onlyRequired for POST/PUT/DELETE requests that carry a body.
There is no bearer token and no custom auth header. Identity comes entirely from a cookie plus the product query parameter. For InstituteType / OrganizationType / Organization that cookie is vacc-account-auth; for the Onboard controller (§8) it is the product SaaS cookie vacc-<product>-auth (e.g. vacc-lms-auth), which also carries the institute context (InstId).

3. Response envelope & error codes

Responses are serialized camelCase, and null properties are omitted. The full shape is:

{
  "success": true | false,
  "message": "human-readable string",          // omitted when null
  "data":    { ... } | [ ... ],                 // omitted when null (present on GET success)
  "errors":  [ { "code": "...", "message": "...", "field": "..." } ]  // omitted when null
}
  • Command success (POST/PUT/DELETE): { "success": true, "message": "<text>" } — no data.
  • Query success (GET): { "success": true, "data": <payload> } — no message.
  • Each entry in errors[] has a machine-readable code; switch on code, not message. field is present for validation / required-field errors.

7. Organization controller

Every endpoint is scoped to the authenticated user (creatorUserId = cookie UserId). A user may own at most 3 non-deleted organizations. Soft-deleted organizations are excluded from the cap and from every read endpoint. See §9 for the isDefault, KYC-upsert, and soft-delete behaviours.

PUT/org

Summary. Updates one organization the caller owns (and upserts its KYC row) in a single transaction. Call this to save the edit form returned by GET /org/edit. Only a row matching orgId + the authenticated user + not soft-deleted is touched; anything else → 404.

Request

EnvironmentMethod & URL
TestingPUT https://api-vacc.vidyaone.com/test/inst/org
ProductionPUT https://api-vacc.vidyaone.com/inst/org

Headers: Cookie: vacc-account-auth=<token>, Content-Type: application/json.   Query: product (required).

Body — payload nested under putDTO:

{ "putDTO": { "orgId": 123, ...same fields as POST postDTO... } }
putDTO fieldTypeRequiredConstraints
orgIdintegeryes> 0. The organization to update; must be owned by the caller and not soft-deleted.
creatorUserIdintegeryes (validation)Must be > 0 or validation fails. The server scopes the update by the authenticated user, not by this value — send the caller's own user id.
All other fields — orgName, orgTypeId, mobile, regNo, regDate, email, address, districtId, stateId, countryId, pincode, logo, isOwner, ownerName, ownerEmail, isWhatsappNumber, isDefault, kyc — carry the same types, requiredness, constraints and defaults as POST /org §7.1.
Every writable column is overwritten with the value you send. There is no partial/patch merge — omitting email sends "" and clears the column. Read the current row with GET /org/edit first and send it back whole.
  • KYC: when kyc is present, an existing tbl_organization_kyc row for this org is updated (and un-deleted if it had been soft-deleted); if none exists, one is inserted and linked. Same transaction as the org update.
  • isDefault: true → within the same transaction, this org is promoted to default and the flag is cleared on the caller's other orgs. isDefault: false leaves the current default untouched.

Response — 200 OK

{ "success": true, "message": "Organisation updated successfully." }

Summary. Bulk soft-deletes one or more of the caller's organizations — sets isDeleted = true and stamps deletedAt. The row is never physically removed. A soft-deleted org no longer counts toward the 3-org cap and disappears from options, listbyuser, view and edit.

8. Onboard controller

Tracks whether an institute has finished onboarding. Route prefix /onboard. Three endpoints, none of which take a request body — every input comes from the cookie and the product query parameter.

Different auth filter. Unlike the other controllers in this guide, Onboard is protected by [SaaSPayload], not [AccountPayload]. It requires the product SaaS cookie vacc-<product>-auth (e.g. vacc-lms-auth) — the one the product web app uses — from which it reads the institute (InstId), the user (UserId) and test mode. Sending only vacc-account-auth yields 401.
  • The tbl_onboard row is created when the institute is created (a different service). All three endpoints assume it already exists and return 404 if it does not.

9. Special behaviours

9.1 Test mode

Prefix the product value with test- (e.g. ?product=test-lms) to run the request in test mode. The prefix is stripped before the product is resolved; the flag is carried through to the handlers. Use the same base URL — test mode is a property of the request, not a separate host.

9.2 Per-user organization cap

POST /org rejects creation with 400 ("You can create a maximum of 3 organizations.") once the caller owns 3 non-deleted organizations. Deactivated orgs still count; soft-deleted orgs do not. The cap is enforced in application code, so a burst of concurrent POSTs from one user can momentarily exceed it.

9.3 Exactly one default per user

Setting a default always clears it elsewhere, in one transaction. Three ways to set it, all equivalent:

  • PUT /org/default with { "orgId": N }.
  • POST /org with postDTO.isDefault = true — the swap runs immediately after the insert.
  • PUT /org with putDTO.isDefault = true — the swap runs inside the update transaction.

isDefault = false on POST/PUT is a no-op for the default flag — it does not clear an existing default. You move the default by promoting another org.

If a user has never set a default, none of their orgs is default — there is no automatic "first org becomes default".

9.4 KYC upsert (PUT /org)

When putDTO.kyc is present: if a tbl_organization_kyc row exists for the org it is updated in place (and un-deleted if it had been soft-deleted); otherwise a new row is inserted and linked. This happens in the same transaction as the org update — if either part fails, neither is applied. POST /org inserts the KYC row in the same unit of work as the org insert.

9.6 Full write / no partial merge

PUT /org overwrites every writable column with the value in the payload. Optional string fields default to "" when omitted, which clears the column. Always load the current row with GET /org/edit, mutate it, and send the whole object back.

9.7 Downstream side effects

None of the four controllers in this guide publish SQS/SNS messages or invoke other Lambdas — the Onboard endpoints only flip flags on tbl_onboard. The service does write to a notification queue for other flows (e.g. trial start), which are out of scope for this guide.
