API reference for the cart / buy-now ingest endpoint — request payload, validation rules, and response shapes.

01 Request payload

JSON object in the HTTP body of a POST request. All field names are camelCase, matching what the vidyaone.com frontend sends directly. 

{
  "productId":    1024,
  "serviceId":    0,
  "serviceCode":  "",
  "planId":       2,
  "guestId":      "guest_a1b2c3d4",
  "userId":       0,
  "quantity":     1,
  "price":        4999.00,
  "discount":     500.00,
  "total":        4499.00,
  "buyNow":       true,
  "payAsGuest":   true,
  "billingCycle": "yearly",
  "subscription": true,
  "pageLink":     "https://vidyaone.com/product/1024"
}

02 Identification rule

Simple version: every item is either a product or a service, never both — and a guestId is always required no matter which.

  • guestId — always required, on every request.
  • productId or serviceId — at least one must be a positive integer. Whichever one you're not using can be 0, left out entirely, or omitted — no error either way.
  • userId — always optional, regardless of whether you used productId or serviceId.

One exception: if you do send a value for the unused field, it can't be negative. productId: -1 is rejected even though serviceId was valid — 0 or omitting the field entirely are the only accepted ways to say "not applicable."

04 Validation & rejection

Structural checks (run first, in order)

  • Body size ≤ 900,000 bytes (900 KB) — checked before JSON parsing.
  • Body must be valid JSON, and must be a JSON object (not an array, string, etc.).
  • Identification rule (see §02) must be satisfied.

Bot / spam heuristic

Three signals; 2 or more firing together flags the request as a bot:

  • Missing User-Agent header
  • Known bot substring in User-Agent (e.g. bot, curl, python-requests, googlebot…)
  • Missing Referer header

Dangerous content scan

Free-text fields (guestId, serviceCode, pageLink, and the User-Agent header) are scanned, case-insensitively, for substrings like <script, javascript:, onerror=, union select, drop table, ' or '1'='1. A match rejects the request. This is a lightweight heuristic, not a WAF.

Both a bot signal and dangerous content produce the same response: 400 { "error": "Submission rejected" } — the specific reason is only visible in CloudWatch logs, not returned to the caller.

Common rejection messages

  • Payload exceeds 900 KB limit
  • Either 'productId' or 'serviceId' must be a positive integer — neither one is positive
  • Field 'productId' must not be negative / Field 'serviceId' must not be negative — the unused field was sent with a negative value
  • Field 'guestId' is required
  • Field 'guestId' contains disallowed characters
  • Field 'buyNow' is required / Field 'payAsGuest' is required — both must be present and a real boolean
  • Field 'quantity' must be between 1 and 1000
  • Field 'billingCycle' must be one of ['monthly', 'yearly']
  • Submission rejected — bot signals or dangerous content detected

05 Example requests

✅ Minimal valid — productId path

{ "productId": 1024, "guestId": "guest_a1b2c3d4", "buyNow": false, "payAsGuest": true }

✅ Minimal valid — serviceId path

{ "serviceId": 7, "guestId": "guest_a1b2c3d4", "buyNow": false, "payAsGuest": true }

userId is optional here too — it's never required by either path. buyNow and payAsGuest are required on every request.

✅ Full subscription example

{
  "productId":    1,
  "planId":       2,
  "serviceId":    2,
  "serviceCode":  "",
  "quantity":     1,
  "price":        200,
  "discount":     0,
  "buyNow":       false,
  "payAsGuest":   true,
  "guestId":      "abc123",
  "userId":       0,
  "billingCycle": "yearly",
  "subscription": true,
  "pageLink":     ""
}

❌ Rejected — no identifier at all

{ "guestId": "abc123" }
// 400 — "Either 'productId' or 'serviceId' must be a positive integer"

❌ Rejected — missing guestId

{ "productId": 1 }
// 400 — "Field 'guestId' is required"

❌ Rejected — missing buyNow / payAsGuest

{ "productId": 1, "guestId": "abc123" }
// 400 — "Field 'buyNow' is required" (payAsGuest is checked next, once buyNow is present)

❌ Rejected — negative value on the unused field

{ "productId": 5, "serviceId": -1, "guestId": "abc123" }
// 400 — "Field 'serviceId' must not be negative" — even though productId alone was enough

❌ Rejected — dangerous content

{ "productId": 1, "guestId": "abc123", "pageLink": "https://x.com/<script>alert(1)</script>" }
// 400 — "Submission rejected"

06 Responses

204 No Content

OPTIONS preflight — returned immediately, no body, no validation performed.

200 OK
{
  "message":   "Item received",
  "requestId": "c4d1e2..."
}

Returned when buyNow is false, after the item is durably written to SQS. SNS publish is best-effort and does not affect this response.

302 Found
Location: https://account.vidyaone.com/checkout

Returned instead of 200 when buyNow is true and the request validated cleanly — the item has already been written to SQS by this point. Body is empty; the destination is only in the Location header, configured via config.CHECKOUT_URL. The frontend/client decides how to navigate there (a real browser form POST follows this automatically; a fetch()-based caller will need to read response.url and navigate manually, since a followed redirect does not move the browser tab on its own).

400 Bad Request
{
  "error":     "Field 'guestId' is required",
  "requestId": "c4d1e2..."
}

Returned for any failed validation rule (specific message) or malformed JSON body (generic "Invalid request body" — no internals leaked).

500 Internal Server Error
{
  "error":     "Internal server error",
  "requestId": "c4d1e2..."
}

Returned only if SQS delivery fails (queue outage, permissions, etc.) or an unexpected exception occurs. A failed SNS publish never causes this — it's logged and swallowed.

07 Request flow

Request → lambda_handler │ ├─ method == OPTIONS? → 204, no processing │ └─ POST → parser.parse(event) │ ├─ size guard ≤ 900 KB, else 400 ├─ JSON decode must be an object, else 400 ├─ identification guestId required; productId or serviceId must be positive (no negatives), else 400 ├─ per-field validation type / range / format checks, else 400 ├─ device + location enrichment (User-Agent, CloudFront headers) ├─ bot heuristic 2+ signals → 400 "Submission rejected" ├─ dangerous content XSS/SQLi patterns → 400 "Submission rejected" │ └─ event built │ ├─ send_sqs() mandatory — failure → 500 └─ publish_sns() best-effort — failure logged, still 200/302 │ ├─ buyNow == true? → 302 redirect, Location: config.CHECKOUT_URL └─ buyNow == false? → 200 "Item received"

Nothing invalid, bot-flagged, or dangerous ever reaches SQS/SNS — every rejection path raises before the message is built or sent.
